\chapter{总结与展望}\label{chap:conclusion}

\section{总结}

论文围绕多校区办学条件下的校园出行问题，完成了一个基于 Spring Boot 的校内综合交通平台原型。课题所面对的并不是抽象的“智慧交通”概念，而是高校内部较为具体的几类矛盾：班车信息分散、拼车协作缺少规范流程、出行行为难以沉淀为后续可用的数据。围绕这些问题，论文依次完成了需求分析、系统设计、功能实现与测试验证。

在系统组织上，平台以微信小程序作为统一入口，后端按照用户、拼车、论坛、聊天、文件和交通几个方向拆分服务。这样的结构与业务特征是对应的：用户和拼车数据具有明显的状态流转关系，论坛和聊天数据则更强调结构灵活与高频读写。围绕这一差异，系统进一步采用 MySQL 与 MongoDB 的组合存储方式，使不同类型数据能够在更合适的环境中落地。

在核心业务上，论文没有把拼车仅仅处理为信息发布，而是将其组织成一条可追踪的完整流程。系统支持订单发布、候选查询、申请审批、行程完成和互评反馈，评价结果还会继续回写到信用统计中，并参与后续匹配。围绕候选排序问题，论文实现了“规则筛选 + 随机森林排序”的二层匹配机制，使系统既能保证候选结果满足基本时空约束，也能在多个可选订单之间给出更合理的优先顺序。

在工程实现上，前端按照页面、组件和服务分层组织，后端按照控制层、业务层和数据访问层划分逻辑。论坛、聊天和交通模块虽然不处于拼车主链中心，但它们共同补足了信息交流、即时确认和基础查询等使用环节，使平台形成了较完整的业务闭环，而不是停留在某个单一功能点上。

从测试结果看，在当前原型规模下，系统已经能够完成主要业务流程，接口交互基本稳定，拼车查询在加入规则计算和模型重排之后仍保持了可接受的响应水平。论文工作的重点，归根到底仍然是面向具体场景的系统落地：不是提出一个抽象的通用模型，而是把校园综合交通服务中原本分散的问题组织到同一平台中加以解决。

\section{展望}

平台目前已经完成基本功能实现，但若要进一步接近长期、真实、稳定运行的状态，仍有若干方面值得继续推进。

首先，拼车排序模型还有进一步深化的空间。当前训练数据主要由模拟样本构成，能够支持原型验证，但距离真实校园出行行为仍有差距。后续如果能够持续积累真实订单、取消记录、等待时长和评价数据，模型训练就可以逐步转向真实业务数据，并据此比较排序学习、图模型或时空序列方法在该场景中的适用性。

其次，系统在服务治理层面的实现仍然偏轻量。随着访问量增加，统一网关、配置管理、链路追踪、日志监控和缓存机制的重要性都会进一步上升。尤其是拼车查询这类包含多步计算和外部服务调用的接口，后续可以结合异步任务处理或缓存策略，继续降低高峰阶段的服务压力。

再次，平台治理问题在更大规模用户条件下会变得更加突出。论坛内容审核、异常行为识别、消息风控和隐私保护，都不再只是附加需求，而会逐步成为平台持续运行的基础条件。当前系统已经具备基础身份认证和信用约束，但若进入长期运行阶段，仍需补充更细致的访问控制和审计机制。

最后，平台的应用边界仍有继续扩展的可能。现阶段系统主要围绕班车查询和拼车组织展开，后续可以进一步接入临时活动接驳、校内摆渡需求分析和线路热度统计等功能，使平台不仅服务于单次出行，也能够逐步支持校园交通管理决策。

总体来看，论文完成的平台已经具备较完整的基础框架，能够支撑校园综合交通服务中的核心流程。若后续能够在真实数据积累、服务治理和平台治理几个层面继续推进，其实际应用价值仍有进一步提升的空间。
