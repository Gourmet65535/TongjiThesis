\chapter{总结与展望}\label{chap:conclusion}

\section{总结}

论文围绕多校区办学条件下的校园出行问题，完成了一个基于 Spring Boot 的校内综合交通平台原型。课题所面对的并不是抽象的“智慧交通”概念，而是高校内部长期存在、但往往分散在不同渠道中的实际问题，例如班车信息不集中、拼车过程缺少稳定流程，以及出行行为难以被系统记录和继续利用。围绕这些问题，论文完成了需求分析、系统设计、功能实现与测试验证。

从系统组织方式看，平台以微信小程序作为统一入口，后端则按用户、拼车、论坛、聊天、文件和交通等业务拆分服务。这样的划分与数据特点基本一致。用户和拼车数据带有较明显的状态变化和约束关系，论坛、聊天和时刻表数据则更强调结构灵活和读取便利。基于这一差异，系统采用 MySQL 与 MongoDB 组合存储，使不同类型的数据能够在更合适的环境中保存和访问。

论文实现的重点放在拼车链路上。系统并没有把拼车理解为简单的信息发布，而是将其组织为订单发布、候选查询、申请审批、行程完成和互评反馈这一连续过程。反馈结果会继续写回用户信用统计，并参与后续匹配。针对候选排序问题，系统实现了“规则筛选 + 随机森林排序”的二层匹配机制。这样处理以后，候选结果先满足基本时空约束，再根据时间差异和信用信息继续区分优先顺序。

在工程实现层面，前端以页面、组件和服务为主要组织单元，后端则沿控制层、业务层和数据访问层展开。论坛、聊天和交通模块虽然不属于拼车主链本身，但它们承担了经验交流、即时确认和基础查询等作用，因此对平台的完整性仍然是必要的。换句话说，本课题完成的不是某一个孤立功能，而是一套能够支撑校园交通日常使用的原型系统。

结合测试结果可以看到，在当前原型规模下，系统已经能够完成主要业务流程，接口交互也保持了基本稳定。拼车查询在加入规则计算和模型重排之后，响应时间仍处于可接受范围内。对本文而言，更重要的意义不在于提出一个通用模型，而在于把校园综合交通中原本分散的服务和流程组织到同一平台中，并验证其具备实际运行的基本条件。

\section{展望}

平台目前已经完成基本功能实现，但如果要进一步接近长期、真实、稳定运行的状态，仍有一些问题需要继续推进。

比较直接的一点在于拼车排序模型。当前训练数据主要来自模拟样本，足以支撑原型验证，却还不能完全代表真实校园出行行为。后续若能持续积累真实订单、取消记录、等待时长和评价数据，模型训练就可以逐步转向真实业务数据，排序结果也会更接近实际使用情况。

另一个需要补强的方面是服务治理。现阶段系统能够完成主要流程，但整体实现仍然偏轻量。访问量上升后，统一网关、配置管理、链路追踪、日志监控和缓存机制的重要性会明显提高。尤其是拼车查询这类包含多步计算和外部服务调用的接口，后续还可以结合异步处理或缓存策略，减轻高峰时段的服务压力。

如果平台面向更大规模的用户持续运行，治理问题也会变得更具体。论坛内容审核、异常行为识别、消息风控以及隐私保护，都不宜再被视为附加项。当前系统已经具备基础身份认证和信用约束，但若进入更长期的运行阶段，还需要补充更细的访问控制和审计机制。

除此之外，平台的应用范围也还有继续扩展的余地。现阶段系统主要围绕班车查询和拼车组织展开，后续可以结合临时活动接驳、校内摆渡需求分析以及线路热度统计等功能，逐步把平台的作用从单次出行服务延伸到交通管理支持。

总体而言，本文完成的平台已经具备较完整的基础框架，能够支撑校园综合交通服务中的主要流程。后续如果在真实数据积累、服务治理和平台运行机制上继续推进，其应用价值仍有进一步提升的空间。
