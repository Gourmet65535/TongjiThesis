\chapter{总结与展望}\label{chap:conclusion}

\section{总结}

本文针对多校区办学条件下校园交通信息分散、拼车组织缺少规范流程以及出行数据难以沉淀等问题，设计并实现了一个基于 Spring Boot 的校内综合交通平台。论文围绕需求分析、系统设计、工程实现和测试验证展开，最终完成了一个包含班车查询、拼车服务、论坛交流、即时沟通和行程反馈等功能的系统原型。

在系统结构上，本文采用微信小程序作为统一入口，以 Spring Boot 构建用户、拼车、论坛、聊天、文件和交通等后端服务。该结构的意义不只是完成前后端分离，更在于为不同类型业务建立相对稳定的边界。用户与拼车数据强调状态与事务，论坛和聊天数据强调结构灵活，这种差异也对应到 MySQL 与 MongoDB 的混合存储方案中。

在核心业务上，本文将拼车场景从简单的信息发布扩展为可追踪的完整流程。系统能够支持订单发布、候选查询、申请审批、行程完成和互评反馈，并将评价结果继续用于信用统计和后续匹配。在此基础上，本文实现了“规则筛选 + 随机森林排序”的二层匹配机制，使系统不仅能筛出满足约束的候选订单，还能对候选结果给出更合理的排序。

在工程实现上，前端通过页面、服务和组件分层组织代码，后端通过控制层、业务层和数据访问层组织各微服务逻辑。论坛、聊天和交通等模块虽然不是拼车主链路的一部分，但它们共同补足了校园出行场景中信息交流、即时确认和基础查询的需要，使平台能够形成较完整的使用闭环。

测试结果表明，系统在当前原型规模下能够完成主要业务流程，接口交互基本稳定，拼车查询在包含规则计算和模型重排的情况下仍保持可接受的响应水平。总体而言，本文的工作更偏向面向具体场景的系统实现：重点不在提出抽象的通用模型，而在于把校园综合交通服务中几个实际分散的问题组织到同一平台中加以解决。

\section{展望}

本系统已经完成基本功能实现，但若面向更长期和更大规模的实际使用，仍有多个方向值得继续推进。

首先，拼车排序模型仍有进一步完善空间。当前训练数据以模拟样本为主，能够支持系统原型验证，但与真实校园出行行为相比仍然有限。后续如果能够持续积累真实订单、取消记录、等待时长和评价数据，模型就可以转向基于实际行为的训练，并进一步比较排序学习、图模型或时空序列方法在该场景下的效果。

其次，系统在服务治理层面还停留在较轻量的实现阶段。随着访问量增长，统一网关、配置管理、链路追踪、日志监控和缓存机制都会变得更加重要。尤其是拼车查询这类包含多步计算和外部服务调用的接口，后续可以结合异步任务或结果缓存进一步降低高峰时段压力。

再次，平台治理能力仍可加强。用户规模扩大后，论坛内容审核、异常行为识别、消息风控和隐私保护都会变得更加重要。当前系统已经具备基础身份认证与信用约束，但若进入真实长期运行阶段，还需要更细致的访问控制和审计能力。

最后，平台的应用边界也可以继续扩展。现阶段系统主要面向班车查询和拼车组织，后续可以考虑接入更多校内出行资源，例如临时活动接驳、校内摆渡需求分析或线路热度统计等功能，使平台不仅服务于单次出行，也能够逐步支持校园交通管理决策。

总体来看，本文完成的平台已经具备较完整的基本框架，能够支撑校园综合交通服务的核心流程。后续工作如果能在真实数据积累、服务治理和平台治理三个层面继续推进，其应用价值还会进一步提高。
