\chapter{系统实现}\label{chap:implementation}

\section{前端实现}

微信小程序前端位于 \texttt{TJ-Transport} 工程中，是平台面向用户的统一入口。系统没有采用单页式混合写法，而是按页面、组件、服务和工具函数组织代码。论坛、交通、拼车、消息和个人中心被设置为五个一级页面，并通过 \texttt{tabBar} 固定在底部导航区，保证主要业务入口稳定可见。系统主要页面的实现效果如\figref{fig:mini-program-pages}所示。

\begin{figure}[!htbp]
  \centering
  \includegraphics[width=0.96\textwidth]{figures/fig-5-1-mini-program-pages.png}
  \caption{小程序主要页面实现效果图}
  \label{fig:mini-program-pages}
\end{figure}

在结构上，页面层负责处理生命周期、用户输入和界面状态，服务层负责调用后端接口并转换返回数据，组件层负责封装列表项、搜索框、聊天气泡等可复用界面单元。这样做的直接收益是，页面不必直接面向后端原始字段编写逻辑，从而减轻不同服务返回格式差异带来的影响。

数据请求没有分散写在各个页面中，而是统一经过 \texttt{utils/request.js} 处理。该模块会根据路径前缀将请求转发到对应后端服务，并统一设置请求头、处理状态码与业务码。页面层只接收已经规范化的数据或异常结果，不必反复编写相似的请求封装和错误判断。这种写法对于多服务系统尤其重要，否则前端代码很容易因为接口差异而变得凌乱。

接口路径由 \texttt{api/endpoints.js} 集中维护。各业务服务文件在此基础上继续封装更具体的方法，例如拼车订单列表查询、帖子详情获取或聊天消息发送等。服务层还负责把后端返回字段转换为前端视图字段，使模板绑定结构保持稳定。这样一来，即使后端个别字段命名有所调整，前端往往只需要改服务层，而无需逐页排查。

页面状态管理依赖微信小程序的 \texttt{data} 与 \texttt{setData} 机制。列表页通常同时维护筛选条件、分页参数、加载状态和结果数据；详情页则维护当前对象、弹窗开关和局部交互状态。对于论坛列表、拼车列表和消息列表这类高频页面，系统还结合下拉刷新、分页加载和条件重置机制，避免重复请求并保证界面状态与数据结果同步。

组件复用在前端实现中占据较大比重。帖子列表项、拼车卡片、消息单元和搜索框都被抽为独立组件，通过 \texttt{properties} 接收数据，再通过 \texttt{triggerEvent} 将操作回传给页面。组件内部只处理局部展示和交互，不承载跨页面业务流程。这样的边界划分使页面脚本更聚焦于实际业务，而不是被重复的界面细节牵制。

媒体处理和表单提交主要依赖微信原生能力完成。论坛发帖支持图片选择与预览，必要时会在前端先做压缩，再通过文件服务上传；拼车发布和申请则在表单提交前完成日期、时间和人数校验，并在关键操作处结合订阅消息授权。前端在这里承担的不是“业务决策”，而是尽量把明显无效输入拦在提交之前。

总体来看，前端实现的重点并不在视觉复杂度，而在于把多个业务入口放进同一小程序后，仍然维持相对清晰的代码边界。页面、服务和组件分层之后，论坛、拼车、交通和聊天等模块能够在同一工程中共享实现方式，这对后续维护是必要的。

\section{后端实现}

\subsection{后端系统架构与服务设计}

后端采用按业务能力拆分的多服务结构。用户、拼车、论坛、聊天、文件和交通分别以独立 Spring Boot 工程存在，各自维护本模块的控制层、业务层和数据访问层。这样做的目的不是单纯追求“服务化”，而是因为本系统同时包含强事务流程和灵活内容数据，把它们混在同一工程中会明显增加维护成本。

在服务内部，控制层负责接收请求并返回统一结构，业务层负责状态流转、规则校验和核心计算，数据访问层负责持久化操作。跨服务调用通过客户端组件封装，例如拼车服务需要获取用户资料时调用用户服务，调用模型预测时连接随机森林服务。后端微服务之间的调用关系如\figref{fig:backend-service-relations}所示。

\begin{figure}[!htbp]
  \centering
  \includegraphics[width=0.75\textwidth]{figures/fig-5-3-backend-service-relations.png}
  \caption{后端微服务调用关系图}
  \label{fig:backend-service-relations}

从\figref{fig:backend-service-relations}可以看出，前端分别与不同业务服务交互，而拼车和论坛又会在运行中进一步访问用户服务。拼车服务还需要调用模型服务完成候选排序。这个结构说明，系统的复杂性主要不在单个服务内部，而在于服务之间如何保持职责边界，同时仍能完成完整业务流程。

单个服务内部的一致性主要依赖事务控制。以拼车申请审批为例，申请状态变化和订单座位变化必须同步提交，否则容易出现数据不一致。跨服务更新则采用业务记录先落库、再调用外部服务更新统计的方式处理，在当前系统规模下，这种策略足以满足工程需要。

\subsection{用户服务实现}

用户服务承担登录、资料维护和信用统计三类任务。用户首次进入系统时，前端提交微信登录凭证，服务端据此换取用户唯一标识，并判断数据库中是否已有对应记录。若记录已存在，则更新资料与登录时间；若不存在，则初始化新用户数据。登录流程如\figref{fig:user-login-flow}所示。

\begin{figure}[!htbp]
  \centering
  \includegraphics[width=0.86\textwidth]{figures/fig-5-4-user-login-flow.png}
  \caption{用户服务登录流程图}
  \label{fig:user-login-flow}
\end{figure}

资料维护功能允许用户查看和更新昵称、头像及联系方式等字段。实现上，这些操作并不复杂，真正需要持续维护的是信用统计项。拼车反馈产生后，用户服务会根据评分、是否迟到和是否完成行程等信息更新信用分、完成率和迟到率。由于这些字段会被拼车排序再次使用，因此服务在这里不仅保存历史数据，也为后续业务提供特征输入。

在数据访问层，用户服务通过标准化仓库接口完成查询和更新。这样可以把实现重点放在登录判断和统计更新逻辑上，而不是耗费在重复的数据库访问代码上。

\subsection{拼车服务实现}

拼车服务处理订单、申请和反馈三类核心对象。订单发布时，系统会校验出发地、目的地、日期、时间范围和座位数量，并在合法后写入数据库。与普通信息发布不同，拼车订单后续还会经历申请、审批和完成等阶段，因此创建时就需要把状态字段和座位字段纳入统一管理。

用户提交申请后，系统首先检查订单是否仍处于开放状态、是否存在剩余座位，以及当前用户是否已经提交过申请。只有这些条件同时满足，申请才会被写入。车主审批申请时，系统需要同步更新申请状态和订单已用座位数，必要时还要在拒绝或撤销场景下回退座位占用。拼车服务的核心处理流程如\figref{fig:carpool-core-flow}所示。

\begin{figure}[!htbp]
  \centering
  \includegraphics[width=0.76\textwidth]{figures/fig-5-5-carpool-core-flow.png}
  \caption{拼车服务核心流程图}
  \label{fig:carpool-core-flow}
\end{figure}

从\figref{fig:carpool-core-flow}可以看到，拼车服务不是若干独立接口的简单集合，而是一条连续的状态链：从订单发布到候选查询，再到申请处理、行程完成和反馈更新，每一步都可能影响下一步能否执行。

反馈机制是拼车服务与用户信用体系连接的关键位置。行程完成后，系统根据订单参与关系确定可评价对象，并对重复评价进行限制。评价结果保存后，再调用用户服务更新统计字段。这样一来，信用数据并不是人工维护的静态分值，而是由实际拼车行为持续推动变化。

\subsection{论坛服务实现}

论坛服务围绕帖子、评论和点赞展开。帖子创建时，系统接收标题、正文、标签和附件地址，并将其组织为文档结构写入 MongoDB。帖子列表读取则主要依赖标签、关键字和时间排序完成，前端展示所需的作者信息通过调用用户服务补全。

点赞和评论实现中，系统没有在每次展示列表时再去统计全部关联记录，而是在帖子文档中维护点赞数和评论数等冗余字段。这样做能够减轻高频列表查询时的计算开销，也更贴合论坛首页的使用方式。对一个以浏览和轻互动为主的校园论坛而言，这种处理比完全依赖实时聚合更务实。

\subsection{聊天服务实现}

聊天服务采用会话与消息分离的结构。会话文档保存参与者及最近更新时间，消息文档保存具体内容、消息类型和不同用户的状态。系统主要支持单聊，重点解决的是“能否快速建立联系并保持消息状态一致”，而不是实现复杂的社交关系网络。

当用户在拼车详情页中点击联系对方时，系统会先判断双方是否已有会话，若已有则直接复用，否则创建新会话。发送消息后，服务同步更新消息记录和会话的最近活动时间。用户进入聊天页面时，系统再按会话维度读取历史消息并更新已读状态，从而保证会话列表与消息列表之间的状态一致。

\subsection{文件服务实现}

文件服务主要为论坛图片上传提供支持。前端选择图片后先将文件提交至该服务，服务端记录文件名、类型、大小、上传用户和时间等元数据，并将实际文件存入本地存储实现。由于文件存储逻辑被单独封装，后续如果需要迁移到对象存储，不必改动论坛和前端的调用方式。

\subsection{交通服务实现}

交通服务负责读取和返回校内班车及相关公交时刻表数据。该服务的数据结构以线路和区段为主，层级关系明显，因此采用文档型存储。服务端在返回数据前会先对文档结构做整理，使前端能够直接按线路和区段展示，而不必再进行复杂转换。这个模块本身规则不多，但它提供的是平台内最基础的一类出行信息。

\section{拼车匹配算法实现}

\subsection{二层匹配机制总体设计}

拼车匹配是本系统区别于普通信息发布平台的关键部分。系统没有把所有订单直接交给机器学习模型评分，而是先做规则筛选，再做模型排序。其原因在于，校园拼车对起点、终点、日期、时间和剩余座位有明确约束，若这些条件本身不成立，模型分数再高也没有实际意义。算法在线执行流程如\figref{fig:matching-flow}所示。

\begin{figure}[!htbp]
  \centering
  \includegraphics[height=0.85\textheight,keepaspectratio]{figures/fig-5-2-matching-flow.png}
  \caption{拼车匹配算法在线执行流程图}
  \label{fig:matching-flow}
\end{figure}

二层机制的第一层负责缩小候选范围，第二层负责在满足约束的候选中区分优先级。这样既能保证结果可解释，也能把模型调用开销控制在较小范围内。

\subsection{规则筛选层实现}

规则筛选层先处理用户输入合法性，再处理候选订单可行性。系统会检查地点是否属于预设范围、起止时间是否合理，并仅从开放状态且日期匹配的订单中继续筛选。随后，算法分别计算起点匹配、终点匹配和时间重叠程度，不满足基础条件的订单会被直接剔除。

在此基础上，系统进一步计算时间中心差、时间兼容标记以及与用户信用有关的辅助特征。规则层不仅完成过滤，还会给候选订单生成初始分数。这个分数综合了空间匹配、时间匹配和发布者信用情况，用于构成后续模型排序的基线。

\subsection{随机森林模型设计}

仅靠人工设定的线性权重，很难覆盖不同特征之间的组合关系。校园拼车中常见的情况是：路线完全一致，但时间略有偏移；或者时间匹配较好，但发布者的履约记录较差。这类差异并不适合只依赖单一规则判断。因此，系统在规则筛选后引入随机森林回归模型，对候选结果进行二次评分。

随机森林由多棵决策树组成，适合处理数值特征与离散特征混合的场景。与单棵决策树相比，它在样本扰动和特征扰动后具有更稳定的泛化表现。对本系统而言，这一点尤其重要，因为拼车数据同时包含地点匹配、时间差异和信用统计等不同类型的输入。

模型输入共 8 个特征：\texttt{startMatch}、\texttt{endMatch}、\texttt{timeOverlap}、\texttt{timeCenterDiff}、\texttt{isTimeCompatible}、\texttt{userCredit}、\texttt{successRate} 和 \texttt{lateRate}。这些特征分别覆盖空间、时间和履约表现三个维度，能够较完整地描述候选订单与用户需求之间的关系。

\subsection{模型训练过程}

由于开发阶段缺少足量真实历史订单，训练数据主要通过模拟样本生成。样本生成脚本并非随意设值，而是围绕拼车业务约束构造特征范围：空间与时间匹配特征控制在合理区间，信用与成功率、迟到率则模拟不同用户画像。目标值由规则评分函数生成，并叠加少量随机扰动，以避免样本完全机械化。

训练阶段使用 \texttt{RandomForestRegressor}。前 8 列特征构成输入矩阵，最后一列为目标分数。训练集与测试集按 8:2 划分，\texttt{random\_state} 固定为 42，以便复现实验结果。模型参数中，\texttt{n\_estimators} 设为 150，\texttt{max\_depth} 设为 12，用于在拟合能力和过拟合风险之间取得平衡。模型训练完成后以 \texttt{joblib} 保存，供在线预测服务加载。

\subsection{模型服务集成与在线排序}

训练完成的随机森林模型被部署为独立服务，并通过接口接收特征数组、返回预测得分。业务系统之所以不把模型直接嵌入拼车服务，一方面是为了便于后续模型更新，另一方面也是为了让算法实现与业务实现保持边界。

在实际查询过程中，拼车服务不会对全部候选结果都调用模型，而是先按规则分数排序，再选取前若干个结果进入模型重排。这一策略符合本系统的数据规模和响应要求：规则层已经能去掉大量明显不合适的订单，模型更适合用来处理高质量候选之间的细微差别。

若模型服务返回有效结果，系统就以模型分数替换原规则分数；若模型服务不可用，则退回规则分排序。这样做的目的是让模型提升排序质量，但不让模型成为系统可用性的单点风险。

\subsection{算法特点与实现分析}

该算法的特点不在于采用了单一复杂模型，而在于把确定性业务约束和数据驱动排序结合起来。规则层负责回答“能不能拼”，模型层负责回答“哪些候选更优先”。二者分工清晰，也更符合校园拼车场景中“先满足可行性，再比较优先级”的实际逻辑。

从工程角度看，算法还兼顾了实时性要求。规则筛选对候选集合做线性处理，模型预测仅作用于排序靠前的一部分候选，因此在线开销相对可控。对校园平台这类规模中等、实时反馈要求较高的系统而言，这种设计比一开始就全面依赖复杂模型更稳妥。

\section{本章小结}

本章说明了系统前端、后端与拼车匹配算法的实现方式。前端围绕页面、服务和组件组织代码，后端按业务拆分服务并通过接口协作，拼车模块则在规则筛选基础上引入随机森林排序，形成了较完整的在线处理链路。
