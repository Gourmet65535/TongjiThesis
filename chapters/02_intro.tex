\chapter{相关技术概述}\label{chap:related-work}

\section{微信小程序前端技术}

微信小程序是平台的用户入口。对校园场景来说，师生已经习惯通过微信获取通知和进入服务，小程序不需要额外安装，接入成本较低。与传统网页相比，小程序在登录授权、消息订阅、图片选择和本地缓存等方面可以直接调用微信能力，很多基础功能不必从头实现。

从工程实现看，小程序前端主要由页面、组件和服务层构成。页面组织业务流程和交互事件，组件负责高频界面单元复用，服务层处理接口调用和数据转换。页面描述使用 WXML，样式使用 WXSS，交互逻辑使用 JavaScript。数据更新依赖生命周期和 \texttt{setData} 完成。虽然这种机制不如通用前端框架灵活，但对本系统这类以列表、表单和消息展示为主的应用来说，足以支撑稳定开发。

这一技术路线与平台的使用方式是匹配的。校园用户的典型操作并不复杂，更多是查看班车、筛选拼车、提交申请、阅读帖子和发送消息。前端侧真正需要处理的，不是复杂动画或重度可视化，而是多页面之间的状态切换、参数传递和接口结果回显。小程序框架在这一点上的约束反而有助于控制代码范围，使页面逻辑不至于过快膨胀。

从实现细节看，小程序原生能力对平台也有直接帮助。登录环节可以接入微信授权流程，减少单独设计账号体系的工作量；拼车申请和订单提醒可以结合订阅消息能力处理；论坛发帖与评论中的图片上传，则可以直接利用媒体选择与文件上传接口完成。对这个项目而言，微信小程序的价值并不在于“新”，而在于它确实能够降低校园场景下的接入门槛和实现成本。

\section{Spring Boot 后端开发技术}

后端基于 Spring Boot 实现。选择这一框架，主要是因为它对 Web 服务、依赖管理和常见组件整合的支持较完整，基础工程搭建成本也相对可控。相关研究表明，Spring Boot 在开发效率、启动性能和资源占用等方面在主流 Java 框架中具有较好的综合表现\cite{jelen2021,ksiazek2022}。对于本课题这样一个由多个业务模块组成的系统而言，如果把大量时间耗在重复配置上，真正留给业务实现的空间就会被压缩，而 Spring Boot 恰好能把这部分工作收得比较集中。

在具体实现中，控制层负责接收请求、解析参数并返回统一响应，业务层负责规则校验和状态处理，数据访问层则通过 Spring Data 完成持久化操作。跨服务调用被封装成独立客户端类，避免在业务代码中反复处理 HTTP 细节。对同时依赖用户服务和模型服务的拼车模块来说，这种组织方式更有利于控制耦合，也方便后续定位问题。

Spring Boot 与本系统的契合点，还体现在它比较适合承载清晰的分层结构。平台虽然规模不算很大，但同时包含用户、拼车、论坛、聊天、文件和交通等多类服务，业务边界并不简单。尤其是拼车服务内部存在连续的状态变化，例如申请提交、车主审批、订单完成和反馈更新，这类处理放在职责明确的后端工程中更合适，而不应散落在控制器甚至前端页面中。

另外，Spring Boot 与测试框架、数据访问组件以及 JSON 序列化工具的整合较为顺畅，这一点对毕业设计项目同样重要。系统不仅要实现功能，还需要说明接口如何组织、数据如何落库、测试如何开展。采用这一框架后，这几部分工作之间可以保持较稳定的衔接关系，也更便于在论文中进行较清楚的工程描述。


\section{微服务接口与服务协同技术}

平台在实现中采用按业务能力拆分服务的方式组织后端，而服务之间的协同主要依赖 HTTP 接口完成。这样做并不是为了刻意把架构做复杂，而是因为系统中的几类数据和流程差异明显。用户服务主要处理身份与信用统计，拼车服务围绕订单和申请展开，论坛与聊天则更偏向内容交互。如果把这些逻辑全部放进单体工程，后续维护时很容易出现边界不清的问题。

在接口设计上，系统使用统一的 JSON 返回结构\cite{fielding2000}。前端在请求成功或失败时，不必分别适配不同服务的返回形式，而是按统一字段读取结果。这个安排看起来只是一个实现细节，但它直接影响前端服务层的封装方式，也影响后续调试和测试时的工作量。

服务协同主要出现在两类场景中。一类是基础数据补全，例如拼车服务和论坛服务需要调用用户服务获取昵称、头像和信用统计；另一类是模型调用，即拼车服务在规则筛选之后，把候选特征发送到独立模型服务进行排序预测。前一种调用反映的是跨模块数据复用，后一种调用则体现了业务系统与算法服务之间的边界。平台的复杂性，很大程度上也正是来自这些协作关系，而不在某一个接口本身。

从实现角度看，采用客户端封装的方式处理服务调用更合适。业务类不必直接书写大量 HTTP 请求细节，而是通过 \texttt{UserClient}、\texttt{ModelClient} 这类组件完成访问。这样做可以把接口地址、请求结构和异常处理集中在一处，也便于后续修改和测试。对论文所描述的工程实现来说，这种组织方式比在业务代码中直接拼装请求更清楚。

\section{数据库与文档存储技术}

系统同时使用 MySQL 和 MongoDB。二者的分工依据是数据形态和一致性要求，而不是简单区分“老技术”和“新技术”。用户资料、拼车订单、申请和反馈都存在明确状态流转和数量约束，需要较强事务支持，因此放在 MySQL 中更合适\cite{gyorodi2015}。关系型数据库提供的唯一约束、索引和事务能力，能够直接服务于座位控制、重复申请检查和评价约束。

帖子、评论、聊天消息和交通时刻表则属于另一类数据：字段更灵活，经常包含数组、嵌套对象或不同类型附件。如果全部拆成关系表，连接和映射成本会明显增加。MongoDB 的文档结构更适合保存帖子附件、消息状态以及时刻表层级信息\cite{sadalage2015}。两者组合使用后，系统在一致性和灵活性之间能够取得较平衡的效果。

这种混合存储方案与平台的实际业务是对应的。拼车业务中，订单状态、座位数量、申请记录和反馈结果之间存在连续约束，如果没有事务支持，状态很容易不同步；而论坛和聊天中的很多内容天然就是文档式结构，例如一条帖子可能同时带有标签、图片附件和冗余统计字段，一条聊天消息又可能附带不同用户的已读状态。把这两类数据强行放入同一种存储模型，都会带来额外成本。

除了数据结构不同，两类数据库的访问模式也有差别。MySQL 更适合处理精确查询、唯一约束和状态更新；MongoDB 更适合按文档整体读取与写回，减少跨表连接。对于校内综合交通平台这种既有强约束业务、又有内容交互功能的系统来说，这种分工是比较自然的。它不是为了“展示技术栈丰富”，而是为了让存储方式尽量贴合业务本身。

\section{随机森林模型服务技术}

平台中的拼车匹配并不只依赖规则筛选。为了在满足基本约束的候选订单之间进一步区分优先级，系统还引入了随机森林模型服务。随机森林本质上属于集成学习方法，能够通过多棵决策树共同完成回归或分类任务。与单一规则打分相比，它更适合处理空间匹配、时间重叠和信用统计这类来源不同、类型不同的特征。

就本课题而言，随机森林被选用并不是因为算法复杂，而是因为它与当前数据条件较为匹配。平台在开发阶段真实样本规模有限，特征数量也相对可控，采用结构过重的模型并不合适。随机森林对特征缩放要求不高，训练和部署成本也相对较低，更适合作为原型系统中的排序模型。正文中提到的空间匹配、时间差异、成功率和迟到率等特征，都可以较自然地组织成模型输入。

在工程组织上，模型并未直接嵌入拼车后端，而是被部署为独立的 FastAPI 服务。拼车服务先完成规则筛选与特征提取，再将候选结果中的特征数组发送到模型服务，接收预测分数后完成重排。这样做有两个直接好处：一是模型更新时不必改动主业务服务；二是当模型服务不可用时，业务系统仍可以退回到规则分排序，避免整个查询接口失效。

因此，随机森林在本系统中的作用，不只是提供一个“算法模块”，而是承担了候选排序精细化处理的职责。它与前面的规则筛选共同构成二层匹配机制，也构成了平台实现中算法服务与业务服务分离的一部分技术基础。

\section{本章小结}

本章介绍了平台实现所依赖的主要技术，包括微信小程序前端、Spring Boot 后端、服务协同方式、MySQL 与 MongoDB 的组合存储方案，以及拼车匹配中使用的随机森林模型服务。后续章节中的模块划分、接口组织、数据落库和算法调用，均建立在这些技术选择之上。
