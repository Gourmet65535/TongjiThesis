\chapter{相关技术概述}\label{chap:related-work}

\section{系统架构与服务组织技术}

本系统采用前后端分离架构。前端负责页面展示、交互组织和本地状态维护，后端负责业务处理、数据访问和服务协同。对本课题而言，这种划分不是单纯出于技术流行，而是因为校园交通场景同时包含列表查询、表单提交、会话消息和多服务协作等多类操作。如果将界面逻辑与业务逻辑混杂在同一工程中，后续维护会很快变得困难。

后端进一步按业务边界拆分为多个 Spring Boot 服务，包括用户、拼车、论坛、聊天、文件和交通等模块。不同服务围绕相对稳定的业务职责组织代码，再通过 HTTP 接口协作。这种方式便于分别处理强事务数据和内容型数据，也便于在后续开发中按模块扩展功能，而不必反复调整整个系统结构。

\section{微信小程序前端技术}

微信小程序是本系统的用户入口。校园用户日常使用微信频率较高，小程序无需单独安装，适合作为校内服务的轻量化载体。与传统网页相比，小程序在登录授权、消息订阅、图片选择和本地缓存等方面能够直接调用微信提供的能力，能够减少一部分基础功能的重复实现工作。

在工程实现上，小程序前端主要由页面、组件和服务层构成。页面负责组织业务流程和交互事件，组件负责高频界面单元复用，服务层负责接口调用与数据转换。页面描述使用 WXML，样式使用 WXSS，交互逻辑使用 JavaScript。数据更新依赖页面生命周期和 \texttt{setData} 机制完成，这种方式虽然约束较强，但对于本系统这样以列表、表单和消息展示为主的应用而言，足以支持稳定开发。

\section{Spring Boot 后端开发技术}

本系统后端基于 Spring Boot 实现。选择 Spring Boot 的原因主要有两点：一是其对 Web 服务、依赖管理和常见中间件整合支持成熟，能够缩短基础工程搭建时间；二是其分层开发方式较清晰，适合按控制层、业务层和数据访问层组织代码，便于维持各模块内部的职责边界。

在具体实现中，控制层负责接收请求、解析参数并返回统一响应；业务层负责状态流转、校验和核心计算；数据访问层则通过 Spring Data 完成持久化操作。跨服务调用通过封装客户端类实现，以减少业务代码中直接处理 HTTP 细节的部分。对一个需要同时连接用户服务和模型服务的拼车模块而言，这种写法有利于控制耦合范围。

\section{数据库与文档存储技术}

系统同时使用 MySQL 和 MongoDB。二者的分工基于数据形态和一致性要求，而不是简单地将“传统数据”与“新型数据”分开。用户资料、拼车订单、申请和反馈都存在明确状态流转和数量约束，需要较强的事务支持，因此存放在 MySQL 中更合适。关系型数据库提供的唯一约束、索引和事务能力，能够直接服务于拼车业务中的座位控制、重复申请检查和评价约束。

帖子、评论、聊天消息和交通时刻表则具有另一类特征：字段结构更灵活，常含有数组、嵌套对象或不同类型附件。这类数据若完全拆成关系表，会增加连接和映射成本。MongoDB 的文档结构更适合保存帖子附件、消息状态以及时刻表层级信息。将二者组合使用，可以在一致性和灵活性之间取得较平衡的实现效果。

\section{本章小结}

本章介绍了系统实现所依赖的几项核心技术，包括前后端分离架构、微信小程序前端、Spring Boot 后端以及 MySQL 与 MongoDB 的混合存储方案。这些技术共同构成了后续系统设计与实现的基础。
