\chapter{相关技术概述}\label{chap:related-work}

\section{系统架构与服务组织技术}

系统采用前后端分离架构。前端主要处理页面展示、交互事件和本地状态，后端负责业务处理、数据访问与服务协同。这样划分并不是为了套用通用开发范式，而是因为校园交通场景同时包含列表查询、表单提交、会话消息和跨服务调用等多种操作。如果把界面逻辑和业务逻辑堆在同一工程里，后续修改任何一个模块都会牵动其他部分。

后端继续按业务边界拆分为多个 Spring Boot 服务，包括用户、拼车、论坛、聊天、文件和交通等模块。各服务围绕稳定职责组织代码，再通过 HTTP 接口协作。这种结构便于把强事务流程与内容型数据分开处理，也更适合在后续开发中逐个模块扩展，而不必反复改动整个工程。

\section{微信小程序前端技术}

微信小程序是平台的用户入口。对校园场景来说，师生已经习惯通过微信获取通知和进入服务，小程序不需要额外安装，接入成本较低。与传统网页相比，小程序在登录授权、消息订阅、图片选择和本地缓存等方面可以直接调用微信能力，很多基础功能不必从头实现。

从工程实现看，小程序前端主要由页面、组件和服务层构成。页面组织业务流程和交互事件，组件负责高频界面单元复用，服务层处理接口调用和数据转换。页面描述使用 WXML，样式使用 WXSS，交互逻辑使用 JavaScript。数据更新依赖生命周期和 \texttt{setData} 完成。虽然这种机制不如通用前端框架灵活，但对本系统这类以列表、表单和消息展示为主的应用来说，足以支撑稳定开发。

\section{Spring Boot 后端开发技术}

后端基于 Spring Boot 实现。选择这一框架，主要是因为它对 Web 服务、依赖管理和常见组件整合支持较成熟，基础工程搭建成本相对较低；同时，它的分层写法比较清晰，便于按控制层、业务层和数据访问层组织代码，保持模块内部职责稳定。

在具体实现中，控制层负责接收请求、解析参数并返回统一响应；业务层负责校验、状态流转和核心计算；数据访问层通过 Spring Data 完成持久化操作。跨服务调用则封装为独立客户端类，避免在业务代码里反复处理 HTTP 细节。对需要同时连接用户服务和模型服务的拼车模块来说，这种做法更容易控制耦合范围。

\section{数据库与文档存储技术}

系统同时使用 MySQL 和 MongoDB。二者的分工依据是数据形态和一致性要求，而不是简单区分“老技术”和“新技术”。用户资料、拼车订单、申请和反馈都存在明确状态流转和数量约束，需要较强事务支持，因此放在 MySQL 中更合适。关系型数据库提供的唯一约束、索引和事务能力，能够直接服务于座位控制、重复申请检查和评价约束。

帖子、评论、聊天消息和交通时刻表则属于另一类数据：字段更灵活，经常包含数组、嵌套对象或不同类型附件。如果全部拆成关系表，连接和映射成本会明显增加。MongoDB 的文档结构更适合保存帖子附件、消息状态以及时刻表层级信息。两者组合使用后，系统在一致性和灵活性之间能够取得较平衡的效果。

\section{本章小结}

本章交代了平台实现所依赖的几项核心技术，包括前后端分离架构、微信小程序前端、Spring Boot 后端以及 MySQL 与 MongoDB 的组合使用方式。后续章节中的模块划分、接口组织和数据落库，基本都建立在这些技术选择之上。
