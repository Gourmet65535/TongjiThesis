\chapter{系统设计}\label{chap:design}

\section{系统总体架构设计}

系统总体设计主要围绕三个判断展开：用户入口要统一，业务边界要拆开，数据存储要贴合数据本身的约束。前端由微信小程序承担，负责页面组织、输入校验和状态展示；后端由多个 Spring Boot 服务分别处理具体业务；数据层则按数据特征分别使用 MySQL 与 MongoDB。总体架构如\figref{fig:system-architecture}所示。

\begin{figure}[!htbp]
  \centering
  \includegraphics[width=0.94\textwidth]{figures/fig-4-1-system-architecture.png}
  \caption{系统总体架构图}
  \label{fig:system-architecture}
\end{figure}

表现层直接面对用户。论坛浏览、班车查询、拼车发布和消息查看等操作，都在这一层完成交互组织。前端除展示数据外，还承担一部分轻量校验，例如表单是否为空、日期时间是否合法、图片是否已选定。这些检查可以挡住明显无效的请求，但不会替代后端的业务校验。

接口层负责前后端之间的请求接入和结果返回。系统采用统一的 JSON 响应结构，前端不必针对每个服务分别适配返回格式。接口层还承担权限校验、参数接收和异常转译等工作，使业务层能够把精力集中在订单状态、用户信用和评论关系等更具体的问题上。

业务逻辑层由用户、拼车、论坛、聊天、文件和交通等服务构成。其中，拼车服务负责核心业务链路，用户服务负责身份和信用数据，论坛与聊天服务负责互动能力，交通服务负责时刻表查询，文件服务为图片上传提供支撑。这样的划分使不同模块可以围绕稳定职责演化，而不必在一个工程中混合处理所有业务。

数据存储层采用混合方案。需要事务与状态一致性的用户和拼车数据存放在 MySQL 中；字段灵活、嵌套明显的帖子、评论、消息和时刻表数据存放在 MongoDB 中。该设计不是为了追求技术多样，而是为了让存储方式与业务约束保持一致。

\section{系统模块设计}

模块设计以业务闭环为主线，而不是简单按页面划分。系统主要包含用户管理、拼车服务、社区交流、聊天与通知以及公共交通信息五个模块。模块之间通过 RESTful 接口协作，尽量避免共享内部实现细节。

\subsection{用户管理模块}

用户管理模块处理三类问题：身份获取、资料维护和信用统计。前两类直接面向前端，后一类则与拼车业务紧密关联。模块内部的核心类关系如\figref{fig:user-class-diagram}所示。

\begin{figure}[!htbp]

  \caption{用户管理模块类图}

在这一模块中，微信登录换取到的唯一标识用于建立系统用户记录，个人资料更新用于支持头像、昵称和联系方式等展示需求，信用统计则为拼车排序和后续行为约束提供数据基础。由于其他模块都依赖用户信息，用户服务在系统中承担的是基础支撑角色，而不是单纯的登录模块。

\subsection{拼车服务模块}

拼车服务模块对应系统最复杂的业务链。它需要处理订单发布、列表查询、申请加入、车主审批、行程完成和评价反馈等一系列状态变化，并在这些状态之间维持数据一致性。模块涉及的核心对象关系如\figref{fig:carpool-class-diagram}所示。

\subsection{社区交流模块}

社区交流模块负责帖子、评论和点赞等内容互动。设计重点在于两点：一是支持标题、正文、标签和图片附件等灵活字段；二是保证点赞和评论数量能够在列表页快速展示。基于这两个要求，模块采用文档型数据存储帖子和评论，并以冗余统计字段减少频繁聚合查询。

从业务作用看，论坛并不是与交通完全无关的附属功能。用户可以在其中发布路线提醒、经验分享和问题讨论，它补充了拼车模块中“只处理订单”的不足，使系统具备面向校园场景的信息交流能力。

\subsection{聊天与通知模块}

聊天与通知模块主要支撑拼车过程中的协同沟通。用户在查看订单或处理申请后，经常需要进一步确认集合地点和时间，因此系统需要提供单聊会话创建、消息发送和未读状态维护等能力。

通知功能与聊天并列设计，是为了让关键业务节点能够及时触达用户，例如申请结果变化、行程完成和反馈开始等。将会话与通知统一考虑，能够减少跨模块跳转带来的信息断裂。

\subsection{公共交通信息模块}

公共交通信息模块负责校内班车及相关公交线路的时刻表管理与展示。该模块业务规则相对简单，但对数据准确性和展示清晰度要求较高。设计时采用稳定的文档结构保存线路、区段和时刻信息，再通过统一接口提供查询能力，以保证前端能够直接展示整理后的结果。

\section{数据库设计}

系统数据库设计遵循“强约束数据进入关系库，灵活内容数据进入文档库”的原则。用户身份、拼车订单、申请和反馈具有明确的状态流转和事务要求，因此使用 MySQL；论坛内容、聊天消息和交通时刻表结构更灵活，因此使用 MongoDB。两类数据库的分工如表\ref{tab:system-database}所示。

\section{接口设计}

系统接口采用 RESTful 风格，并统一使用 ``/api/\{module\}/\{action\}'' 形式组织路径。所有接口都返回统一结构，便于前端集中处理成功与失败结果。接口设计按模块展开，分别对应用户、论坛、拼车、聊天和交通等功能。

\subsection{用户模块接口设计}

用户模块接口主要承担身份进入、资料维护和统计更新三类工作。由于其他模块都会引用用户资料，因此用户接口在系统中具有基础支撑作用。
